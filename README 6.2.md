# Практична робота 6.1 — Базовий State Management

**Дисципліна:** Програмування для мобільних платформ  
**Варіант 2:** Список справ  
**Застосунок:** «Мої справи»  
**Стек:** Flutter SDK, Dart, Material 3. Без provider, bloc, riverpod та інших пакетів керування станом.

## Мета

Навчитися відокремлювати чернетки й фільтри інтерфейсу від спільних даних застосунку.
Реалізувати один застосунок двома способами: підняття стану до предка та надання
стану через ChangeNotifier з InheritedNotifier. Зберегти локальні поля введення
при оновленні списку справ.

## Можливості

1. Додавання справи з назвою та необов’язковим описом. Назва з пробілів не приймається.
2. Позначення виконання прапорцем. Статистика в AppBar оновлюється з того самого списку.
3. Видалення свайпом справа наліво через Dismissible. Кнопка «Скасувати» у SnackBar
   повертає справу разом із її описом і статусом виконання.
4. Фільтри «Усі», «Активні», «Виконані», окремі повідомлення для порожнього списку
   та порожнього результату фільтрації.
5. Окремий екран редагування. «Зберегти» застосовує зміни до спільної моделі та
   повертає до списку; «Скасувати зміни» залишає збережену справу незмінною.
6. Новіші справи розміщуються зверху. Після скасування видалення порядок відновлюється
   за стабільним id. Повторне відновлення тієї самої справи не створює дубліката.

Дані зберігаються лише в пам’яті. Повний перезапуск очищує список — постійне
збереження не входить до вимог цієї роботи. Зміни чернетки застосовуються кнопкою
«Зберегти», без повторного завантаження даних чи перезапуску списку.

## Етап 1 — stage-1-lifting

```bash
git switch --detach stage-1-lifting
flutter pub get
flutter run -d chrome
```

Найближчий спільний власник даних — State кореневого TodoApp, який охоплює обидва
екрани навігації. Він створює звичайну TodoModel і виконує зміни через
`_mutate(VoidCallback action) => setState(action)`.

Модель передається вниз конструкторами. Команди повертаються колбеком mutate.
TodoScreen передає їх формі та списку, список — екрану редагування. Оскільки setState
викликається високо в дереві, перебудови ширші. Фільтр залишається локальним полем
TodoScreen, а чернетки — у контролерах відповідних форм.

## Етап 2 — stage-2-inherited

```bash
git switch --detach stage-2-inherited
flutter pub get
flutter run -d chrome
```

TodoModel успадковує ChangeNotifier. Після фактичної зміни викликається
notifyListeners(). TodoScope успадковує InheritedNotifier<TodoModel> і розташований
над MaterialApp, тому доступний також маршруту редагування.

- `TodoScope.of(context)` реєструє залежність від повідомлень моделі. Використовується
  лише у StatsBadge та TodoList.
- `TodoScope.read(context)` отримує модель без реєстрації залежності. Використовується
  для команд із форм і для видалення.
- Проміжний TodoScreen не отримує й не передає спільну модель чи колбеки.
- До редактора передається один незмінний знімок обраної справи для початкової
  чернетки. Збереження відбувається через TodoScope за id, а не через колбеки предків.

Повернутися до основної гілки: `git switch main`.

## Таблиця стану

| Дані | Тип | Де живуть | Чому |
|---|---|---|---|
| Перелік справ | Стан застосунку | TodoModel, власник — TodoApp | Спільний для списку, редактора і статистики |
| Статус виконання, назва, опис збереженої справи | Стан застосунку | Незмінні Todo у моделі | Усі екрани повинні бачити узгоджені дані |
| Фільтр | Ефемерний | TodoScreen, setState | Впливає на відображення, не змінює самі справи |
| Назва та опис нової справи | Ефемерний | TextEditingController у AddTodoForm | Чернетка не має змінювати спільний список |
| Чернетка редагування | Ефемерний | Контролери EditTodoScreen | Можна відмовитися від змін |
| Кількість виконаних | Обчислюване значення | completedCount моделі | Обчислюється зі списку без дублювання даних |
| Видалена справа для «Скасувати» | Тимчасовий стан дії | Замикання SnackBarAction | Потрібна тільки протягом можливості скасування |

Поля введення зберігаються в локальному State через контролери, фільтр — через
setState. Обидва TextEditingController кожної форми звільняються у dispose().
TodoApp звільняє свою TodoModel у dispose(). Власних таймерів і потоків немає.

## Модель та структура коду

Todo — незмінний клас із final-полями, const-конструктором та copyWith.
Модель не відкриває змінюваний список: items повертає List.unmodifiable.

| Метод TodoModel | Призначення |
|---|---|
| add | Перевірити назву, прибрати зовнішні пробіли, додати справу |
| toggle | Замінити справу копією з протилежним статусом |
| update | Оновити назву й опис, зберегти id та статус |
| remove | Видалити за id, повернути видалений об’єкт |
| restore | Відновити без дублювання, зберегти порядок |

Файли:

- `lib/main.dart` — запуск, тема, власник моделі та dispose.
- `lib/models/todo.dart`, `todo_filter.dart` — справа й перелік фільтрів.
- `lib/state/todo_model.dart`, `todo_scope.dart` — спільні дані й доступ до них.
- `lib/screens/todo_screen.dart` — головний екран і локальний фільтр.
- `lib/screens/edit_todo_screen.dart` — редактор із валідацією.
- `lib/widgets/add_todo_form.dart` — локальна форма створення.
- `lib/widgets/todo_list.dart` — фільтрація, прапорці, Dismissible, перехід до редактора.
- `lib/widgets/stats_badge.dart` — статистика в AppBar.
- `test/` — модельні та віджетні тести.

## Доказ перебудов

У ключових віджетах є debugPrint. Додайте справу, введіть у форму нову чернетку,
приберіть фокус із поля, очистіть консоль і позначте існуючу справу виконаною.

**Очікуваний журнал, ще не фактичний результат:**

```text
build: StatsBadge
build: TodoList
```

Порядок рядків може відрізнятися. Не повинно бути `build: AddTodoForm`,
`build: TodoScreen` чи `build: TodoApp`. Чернетка має залишитися в полі.
Тест `test/rebuild_test.dart` перевіряє цей набір перебудов і збереження тексту.

InheritedNotifier повідомляє всіх своїх залежних віджетів, а не відстежує вибрані
поля. Ізоляція тут досягається тим, що форма не викликає of(context), а в дереві
використовується const AddTodoForm. У разі зміни теми чи параметрів екрана можливі
інші закономірні перебудови; експеримент стосується саме зміни статусу справи.

Фактичний журнал після запуску потрібно додати у [docs/rebuilds.md](docs/rebuilds.md)
і замінити ним очікуваний приклад у цьому розділі.

## Висновок

У підготовленій реалізації список справ є спільним станом, а чернетки та фільтр —
локальними. Перший етап демонструє конструктори, колбеки та setState спільного
предка. Другий відокремлює модель зі сповіщеннями та прибирає передавання спільних
даних через проміжні віджети. Для остаточного підтвердження потрібні локальний
запуск, чистий аналізатор та фактичні докази перебудов.
